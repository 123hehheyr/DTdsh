# Agent Note: 协作式 Session 列表投影读取

Status: implemented

[English](2026-09-30-session-list-host-fairness.md) | 中文

## 问题

Session 列表异步读取 header，随后在一个同步批次内计算缓存投影摘要。即使单个视图很小，较大的插件状态也会让整批计算阻塞无关的 Host 工作。真实 Host profile 定位到了重复的检查点解码；CPU 采样本身并不能证明提速。

## 决策

[ApiSessionList](../../../../packages/api/session-controller/src/list.ts) 在每个完整的 live 或 cold 摘要之后让出 Node 事件循环，包括最后一行。每次让出之后检查取消信号，取消时拒绝返回部分结果。每个摘要仍同步计算。在按活动时间稳定排序之前，live 摘要仍排在 cold 摘要之前；列表不承诺跨 Session 的原子快照。[缓存行身份与优先级规则](../architecture/2026-09-19-projection-cache-listing-identity-and-cached-rows.zh.md)保持不变。

[投影列表基准](../../../../benchmarks/session-corpus/projection-list.bench.ts)补充已有的[会话集合吞吐量用例](../testing/2026-09-28-session-corpus-performance.zh.md)。它使用真实构建产物中的 Session Controller、查询引擎、JSONL 持久化、投影注册表与缓存，以及 storage domain。只有列表路径以外的集成不执行实际操作。每个全新子进程写入确定性生成、带校验和的 Zstd header 和投影记录，关闭写入方，再挂载全新的读取方。不使用录制的用户内容。

| 负载 | Session 数 | 投影观测行数 | 请求记录数 | 未压缩状态 JSON |
|---|---:|---:|---:|---:|
| 适中 | 50 | 4,925 | 641 | 1,813,852 bytes |
| 尾部 | 300 | 300,000 | 37,575 | 111,255,440 bytes |

每个 Session 的行数按基础数量的 50%、75%、100%、175% 循环分布，两种负载的基础数量分别为 100 和 1,000。行中包含嵌套计数器、文本、标签和请求引用；wire view 只返回摘要计数器。这些观测是生成的投影初始状态，不是伪造的持久化 Session 事件。列表不能读取正文，因此只有 header 的日志就足够。

每个子进程分别测量首次列表和三次重复列表，包括 JSON 序列化。准备过程和显式 GC 不计入耗时。GC 后采样堆与 RSS 时，完整结果及其 JSON 仍可达；峰值 RSS 包含整个进程生命周期，包括准备阶段。直方图在工作开始前启用，完成后等待采样以包含最后一次停顿。由视图触发的 immediate 记录排队 Host 工作的等待；这不测量浏览器输入、网络传输或绘制。

最多只有一个探针 immediate 在等待。每次回调完成后，后续视图重新设置探针，因此 `maxViewsPerBatch === 1` 保护整份列表，而不只是第一次让出。原始同步循环以 300 失败；只在第一行让出的变体以 299 失败。墙钟延迟仅作诊断，不作为依赖调度器时机的断言。粗粒度吞吐量上限使用共享的 500 ms 参考余量、2 倍时间系数和 1.25 倍波动余量，得到 1,250 ms。常驻堆使用 240 MiB，且只乘 1.25 倍波动余量，得到 300 MiB。

## 考虑过的替代方案

**缓存解码后的投影状态。** 试验改善了重复列表，却为每份存储行多保留了一份对象图：约 189 MB 变为 346 MB，首次读取也变慢。它还改变了 schema transform 的重复执行语义，并需要明确别名所有权。让出事件循环避免了这些成本，也不削弱状态或 wire 校验。

**缓存或截断 wire view。** 动态视图选择可能在两次读取之间变化，消费者也需要每个当前可用的投影提示。复用或过滤会改变行为，而不是消除整批阻塞。

**只让出一次，或者使用已完成的 Promise。** 只在第一行让出仍会使剩余批次同步执行；微任务不能让事件循环处理排队的 Host 工作。有界 immediate 探针会拒绝这两种公平性退化。

## 后果

Host 能在摘要之间处理其他工作，无需存储额外投影状态。[确定性调度测试](../../../../packages/api/session-controller/tests/list-scheduling.host.spec.ts)固定了中间行和最后一行的让出、取消原因、空行和省略行、稳定并列排序，以及接入、移除和状态变化的交错行为。已有的 Client 变更重放和 cached/sequenced 优先级继续协调进行中的列表读取。

单个大投影、最终排序和响应序列化仍同步执行。多个并发列表可能在同一个事件循环轮次内累积工作，因此这不是全局停顿的硬上限。它明确用少量列表总耗时换取 Host 响应能力，不宣称降低模型延迟、减少解析量或实测改善浏览器绘制。
